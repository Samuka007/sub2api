# 测试代码优先审查方法

## 审查顺序

1. 先读需求、设计、PR 描述和变更摘要。
2. 再读测试，判断测试是否证明需求。
3. 最后读实现，判断实现是否被测试保护。

如果测试无法证明关键行为，报告应先写测试缺口，再写实现风险。

## 必查测试方法

| 方法 | 用途 | 审查问题 |
| --- | --- | --- |
| 等价类划分 | 输入空间很大时分组 | 是否只测了一个正常样本 |
| 边界值分析 | 金额、数量、分页、长度、时间 | 是否测了 0、1、最大值、空值、超限 |
| 判定表 | 多条件组合 | 是否遗漏条件组合和优先级 |
| 状态迁移测试 | 订单、任务、审批、支付状态 | 是否测非法迁移、重复事件、回滚 |
| 异常路径测试 | 外部依赖失败 | 是否测超时、错误码、异常、重试后失败 |
| 幂等测试 | 重复请求、重复回调 | 是否证明重复执行不会重复扣款/写入 |
| 契约测试 | 跨服务或 SDK 调用 | mock 是否来自真实契约 |
| 回归测试 | 修 bug 或补漏洞 | 是否先复现旧问题，再证明修复 |

## Mock 使用规则

允许 mock：

- 隔离不可控外部系统。
- 模拟已知契约中的错误码、超时、边界响应。
- 验证调用方在明确契约下的行为。

禁止 mock：

- 没找到真实接口就自行编一个响应。
- 只让 happy path 通过。
- 用 mock 证明“已经联调”。
- 断言 mock 被调用次数，却不验证业务结果。

## 测试假阳性信号

- 没有断言业务状态，只断言“不报错”。
- 只验证函数被调用，不验证结果。
- mock 数据和真实 DTO/接口文档对不上。
- 测试名描述需求，断言却只覆盖实现细节。
- 异常路径没有断言错误传播、回滚、补偿或状态保持。
- 快照过大，无法说明关键行为。
- 测试修改了实现可见性或加 test-only 入口。

## 联调类变更最低测试线

涉及跨服务调用时，至少审查这些 case：

- 正常返回。
- 外部服务超时。
- 外部服务返回业务失败。
- 外部服务返回格式变化或缺字段。
- 重复请求或重复回调。
- 调用成功但本地落库失败。
- 本地成功但后续通知失败。
- 金额、状态、幂等 key、trace id 等关键字段。

缺少真实仓库或文档时，报告应写：

> 未找到 `{service}` 的真实接口契约，当前测试中的 mock 不能证明联调正确。需要补充 `{repo/doc/api}` 后再判断。

## 优先级

- `Critical`：测试会假通过，且可能掩盖数据错乱、安全风险、资金/订单/权限错误。
- `Important`：关键路径缺少失败、边界、幂等、状态迁移或契约测试。
- `Minor`：测试可读性、重复 setup、命名不清，但不影响行为证明。
