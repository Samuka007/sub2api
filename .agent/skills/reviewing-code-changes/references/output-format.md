# 中文评审报告格式

## 顶部结论

```markdown
## 结论

- 建议：阻塞合入 / 有条件通过 / 可以合入
- 总体置信度：0.xx
- 最大风险：一句话说明
- 证据完整性：已找到哪些代码/测试/文档；缺少哪些联调依据
```

## 必须先修

每个高优先级问题使用固定结构：

```markdown
### P0/P1. 标题

- 位置：`path/to/file.py:42`
- 类型：测试缺口 / 假阳性 / 实现缺陷 / 联调依据缺口 / 安全风险
- 置信度：0.xx
- 证据：代码、测试或文档证据
- 问题：直接说明错在哪里
- 风险链条：从当前代码如何走到用户影响
- 通俗类比：使用非动物类比，例如“像只检查门铃响没响，却没检查门有没有真的锁上”
- 修复建议：具体改什么
- 应补测试：具体测试名称、输入、断言
```

## 测试缺口

优先列测试问题：

- 缺少哪些边界值、等价类、判定表、状态迁移、异常路径、幂等或契约测试。
- 哪些 mock 不可信，为什么不可信。
- 哪些测试断言太弱，可能假通过。

## 实现风险

只列有证据的问题：

- 逻辑错误。
- 错误处理。
- 状态一致性。
- 安全、并发、性能。
- 可维护性中会影响后续修改的真实风险。

## 联调依据缺口

列清楚缺什么，不猜测：

```markdown
- 未找到支付服务仓库：已搜索 `~/work`，关键词 `payment/pay/payOrder`。
- 未找到接口契约文档：本地 docs 和 Yuque 搜索无结果。
- 因此不能确认当前 mock 响应是否符合真实接口。
```

## 低置信度/未采纳发现

```markdown
- `path:line`：发现摘要。裁定：disputed/rejected。原因：证据不足/反方有有效反证。
```

## 建议验证命令

```bash
# 只列真实可运行或用户需要补充信息后才能运行的命令
```

## 禁止写法

- “应该没问题”
- “看起来可以”
- “建议多写点测试”
- “可以 mock 一下证明”
- 没有位置、证据、风险链条的泛泛建议
